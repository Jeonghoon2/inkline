# 개념 사전 (예시 — 개념 하나)

## 나눠 읽기(스트리밍)
DB에서 결과를 한꺼번에 받으면 메모리 사용량이 데이터 양에 비례해 커진다(32만 줄이면 32만 줄만큼). 정해진 개수(이번엔 5천 줄)씩 받아 처리하고 버리면, 데이터가 얼마나 많든 메모리는 그 묶음 크기만큼만 쓴다. 이번에는 DB 쪽에 결과를 둔 채 조금씩 꺼내 오는 '서버 쪽 커서'를 썼다.
- Q: 한꺼번에 읽기가 왜 위험한가?
  A: 메모리 사용량이 데이터 양에 정비례(O(N))해서, 오늘은 괜찮아도 데이터가 늘면 언젠가 상한을 넘는다. 나눠 읽으면 사용량이 묶음 크기로 고정(O(묶음))된다.
- Q: DB에서 나눠 읽는 방법에는 무엇이 있고, 어떻게 다른가?
  A: ① LIMIT/OFFSET: 단순하지만 OFFSET이 커질수록 건너뛸 줄을 매번 다시 읽어 느려진다. ② 키 기준 이어 읽기(WHERE id > 마지막 id ORDER BY id LIMIT n): 색인을 타서 몇 번째 묶음이든 빠르다. ③ 서버 쪽 커서: 질의는 한 번만 하고 DB가 결과 위치를 기억해 n줄씩 내준다.
- Q: 서버 쪽 커서의 단점은?
  A: 다 읽을 때까지 트랜잭션과 DB 연결을 붙잡고 있다. PostgreSQL에서는 긴 트랜잭션이 VACUUM(지운 줄 청소)을 막아 표가 부풀 수 있고, 트랜잭션 단위로 연결을 돌려 쓰는 연결 풀(PgBouncer 트랜잭션 모드 등)과는 잘 맞지 않는다.
- Q: 묶음 크기(5천 줄)는 어떻게 정하나?
  A: 너무 작으면 DB와 주고받는 횟수가 늘어 느려지고, 너무 크면 메모리 이점이 줄어든다. 한 줄의 크기 × 묶음 크기가 메모리 예산 안에 넉넉히 들어오는 선에서, 속도가 더 좋아지지 않는 지점을 측정해 고른다.
