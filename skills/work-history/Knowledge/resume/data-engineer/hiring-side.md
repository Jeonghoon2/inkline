# 데이터 엔지니어 — 새 자료 (조사 2026-10-20)

## 요점 — 이 직무 이력서는 이렇게 쓴다
- 국내 데이터 엔지니어 공고는 두 갈래다. 플랫폼 구축 초기 단계는 특정 스택을 필수로 두지 않고 프로그래밍 기본기를 보며, 백엔드·앱 개발자의 전직 기회로 읽힌다. 고도화 단계는 이미 정해진 스택(Spark·Kafka·Airflow)의 숙련을 요구한다. 지원할 회사의 단계부터 가려야 한다. (새로움) [2][3]
- 같은 글이 스타트업의 소규모 데이터에 분산 시스템을 쓰는 것은 과한 설계일 수 있다고 본다. Spark 없이 Python·SQL 배치로 풀었다는 서술이 그런 회사에서는 약점이 아니다. [2]
- 대기업·중견의 경력직 공고(코웨이 예: 4~10년)는 PySpark·Airflow·Glue 운영 경험을 자격 요건에 명시한다. 이 공고군에는 배치 중심 경력으로 맞추기 어렵다. [4]
- 신입·주니어 서류에서는 도구 개수보다 데이터 흐름(수집→적재→정제→활용)을 하나 깊게 설명하고 본인 기여도를 분명히 쓰는 쪽을 권한다. 프로젝트는 2~3개면 충분하다. [1][5]
- 수치는 규모(일일 처리 건수, 소스 수), 소요 시간(배치 시간 단축), 품질(결함·실패 적재 건수), 비용(스토리지·컴퓨트), 안정성(실패 실행 횟수, 재처리 방식) 중 하나 이상을 넣는다. 실제 수치가 없으면 산출물·개선을 서술하고, 재처리 방식·스키마 설계 의도·운영 안정성도 면접 포인트가 된다. [5][6][7]
- 수치의 출처는 로그, 클라우드 청구서, 모니터링, 이슈 트래커, Git 이력에서 찾는다. 정확한 값이 없으면 정직한 근사치를 쓰되 쓸 수 없는 값은 만들지 않는다. [7]
- 쓴 적 없는 도구는 쓰지 않는다. 설명할 수 있는 도구만 나열하고, 개념만 공부한 도구를 경험처럼 쓰지 않는다. 많은 주니어 역할이 Airflow·Spark를 요구하지 않고 SQL·Python·파이프라인 기본기를 더 본다. (새로움) [8][5]
- 면접은 SQL 확인(조인 중복 원인, 윈도 함수, NULL, 결과 검증)이 거의 항상 나오고, 쏘카 사례에서는 포트폴리오 질문과 코딩 3문제 후 정답보다 접근 논리를 보았다고 한다. 이력서의 모든 줄을 면접 질문으로 바꿔 답을 준비해 둔다. [1][5][6]
- 신입은 이력서만으로 차이를 내기 어려우니 작은 ETL을 직접 만들고 블로그에 기록하라는 조언이 나온다. 경력이 몇 년 있으면 실제 운영 기록(실패 처리, 재실행, 비용)이 그 역할을 한다. [1]
- 백엔드 경력과 데이터 경험을 함께 보여주면 스타트업·플랫폼 구축 단계 공고에 맞고, API 개발이 병행되는 자리에서는 소프트웨어 엔지니어링 역량이 오히려 유리하다. [2][3]

## 기존 자료와 부딪히는 점
- 기존 목록의 datacamp 이력서 글·github data-engineer-handbook은 도구 목록(Spark·Airflow 등)을 갖추라는 쪽에 가깝다. 이번 자료는 회사 단계에 따라 스택을 필수로 보지 않는 공고도 있고 분산 시스템이 과한 경우도 있다고 하여 방향이 다르다. 다만 경력직 대기업 공고[4]는 기존 자료처럼 Spark·Airflow를 명시하므로 둘 다 맞고 공고 유형에 따라 갈린다.
- 못 찾은 것: 국내 데이터 플랫폼 팀이 '서류에서 무엇을 보는지'를 직접 쓴 기술 블로그 글은 검색으로 찾지 못했다(쏘카 회고[1]가 가장 가까움). 공개된 데이터 엔지니어 레벨 정의(주니어·미들 구분)도 권위 있는 것은 찾지 못했고, 블로그 수준의 '주니어 0~2년, 미들 2~5년, 미들은 설계·도구 선택까지 단독 수행' 정도가 검색 요약에만 있어 요점에는 넣지 않았다.
