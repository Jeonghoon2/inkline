# 이력서 구조 (직무 공통)

직무와 상관없이 지켜야 하는 뼈대. 직무별 차이는 각 직무 폴더의 `resume-patterns.md`.

## 핵심 정리
- 읽는 시간은 짧다. 원티드 아티클은 담당자가 한 장을 보는 시간을 "최대 15초 내외"로 본다 → 위 1/3 에 직무 키워드·대표 성과가 보여야 한다
- 순서: 이름·직무 한 줄 → 연락처·링크 → 간단 소개(2~4줄) → 경력(최신순) → 프로젝트 → 기술 → 교육·자격. 경력 3년 미만이면 교육을 조금 올려도 된다(Tech Interview Handbook)
- 여러 직무에 지원하면 **직무별 2~3개 버전**을 둔다(원티드). 같은 사실을 직무에 맞게 고르고 순서를 바꾸는 것이지, 사실을 바꾸는 것이 아니다
- 프로젝트마다 성과 3~5개. "모든 일"이 아니라 "직무가 묻는 일"을 고른다
- 기술은 면접에서 설명할 수 있는 것만. "자신 있는 기술만 기재"(원티드), DataCamp 는 "Only include tools you can discuss confidently"
- 한 장(신입·주니어) ~ 두 장(경력). 줄글보다 한 줄 성과

## 하기 / 하지 않기
- 하기: 제목 줄에 지원 직무 이름(예: '백엔드 개발자'), 간단 소개는 이력서를 다 쓴 뒤 마지막에 요약해 쓴다(인프런)
- 하기: 결과물 링크(GitHub·배포 주소·문서)를 붙이고, 링크가 살아 있는지 확인한다(서버가 꺼진 데모·README 없는 저장소는 감점)
- 하지 않기: 사진·주소·생년월일, 진부한 소개("열정적인", "끊임없이 배우는"), 할 줄 아는 기술 전부 나열
- 하지 않기: 없는 경력 지어내기 — 면접·평판 조회에서 드러난다(원티드)

## 공개 이력서 모음에서 본 구조 (개인정보는 옮기지 않음)
- GitHub 에 마크다운으로 올린 한국 개발자 이력서(예: JSpiner/RESUME)는 대개 `소개 → 경력(최신순) → 활동(멘토링·발표) → 교육 → 오픈소스 기여(PR 링크) → 기술 → 수상` 순서다
- 오픈소스 기여를 PR 링크로 묶어 보여 주는 방식, 동료 추천사를 붙이는 방식이 눈에 띈다 — 확인 가능한 증거를 링크로 단다는 공통점
