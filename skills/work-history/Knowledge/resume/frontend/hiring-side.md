# 프론트엔드 엔지니어 — 새 자료 (조사 2026-10-20)

한계: 토스 · 당근 · 네이버 · 우아한형제들의 "서류에서 무엇을 보는지" 직접 쓴 면접관 글은 검색으로 찾지 못했다. 토스 공고 원문은 차단(403) 또는 잘림으로 열지 못했다. 채용 쪽 근거는 공고(자격요건 · 우대 · 전형)가 가장 단단하고, 나머지는 약한 근거다.

## 요점 — 이 직무 이력서는 이렇게 쓴다
- 기술 스택 나열보다 "실제 서비스 화면을 구현 · 운영하며 문제를 푼 경험"을 앞에 둔다. 채용 쪽 글도 같은 순서로 본다고 쓴다 [1]
- 성능은 지표 + 기법을 한 줄에 쓴다(LCP · 번들 크기 · Lighthouse 개별 지표 + 코드 스플리팅 등). 성능 수치가 하나도 없으면 성능을 맡아 본 적이 없다는 신호가 된다는 조언이 있다 [2]. 예시 수치는 모두 가짜 견본이라 그대로 베끼지 말고 자기 측정값으로 쓴다 [2]
- 접근성은 기준(WCAG 버전 · 등급), 범위(어느 화면), 해결 건수를 적는다. 디자인 시스템은 컴포넌트 수 · 적용 화면 수 · 개발 시간 변화로 쓴다 [2]. 카카오엔터프라이즈 공고도 웹표준 마크업을 자격요건, SEO · 접근성 마크업과 디자인시스템을 업무 · 우대로 둔다 [4]
- 공고가 실제로 묻는 키워드(TypeScript · React/Next.js · 모노레포 · UI 테스트 · CI/CD · 마이크로 프론트엔드)를 자기 경험과 1:1로 맞춘다 [4] (새로움: 국내 대기업 FE 공고 원문 기준)
- 포트폴리오에서는 사용자 흐름 · 화면 설계 판단, 성능 개선 사례, 기획 변경에 버티는 구조를 본다고 한다. 면접은 용어 설명보다 UX · 성능을 고려해 판단한 경험과 오류 · 성능 문제를 진단한 과정을 묻는다 [1]
- 서류는 결국 면접 질문 설계 도구다. 자신 있는 프로젝트와 질문받고 싶은 키워드를 서류에 미리 심어 둔다 [5] (새로움, 단 카카오 공채 후기이고 FE 전용 아님)
- 주니어 → 미드 신호는 "독립적으로 기능을 끝까지 배달"하는 신뢰도, 미드 → 시니어는 모호한 문제에서의 트레이드오프 판단 · 접근성 · 성능 · 팀 간 UI 계약이다. 주니어라면 "혼자 한 기능 단위의 소유권"과 로딩 · 빈 · 오류 상태, 테스트까지 쓰는 쪽이 맞다 [3] (새로움, 단 비공식 일반론)
- Electron 경험은 "사용했다"가 아니라 메인 / 렌더러 프로세스 구조, IPC 보안, 코드 서명 · 자동 업데이트, 웹과 데스크톱 공용 UI 분리로 풀어 쓴다는 공고가 있다 [7] (새로움, 검색 요약)
- 백엔드 비중이 큰 일을 프론트엔드 성과처럼 쓰지 않는다. 풀스택이면 FE 이력서에서는 화면 · 사용자 영향 쪽 성과를 앞에 둔다 [2]
- 토스 계열 공고는 지식의 양보다 새 기술을 빠르게 배워 적용하고, 개발 환경 변화까지 끝낸 경험을 중시한다고 쓴다 [6] (검색 요약)

## 기존 자료와 부딪히는 점
- 기존 이력서 사이트(enhancv · beamjobs · resumegeni)와 방향은 같다(지표 + 기법). 다만 이번 [2]도 같은 부류라 채용 쪽 독립 근거가 아니다. 독립 근거는 [4][6][7] 공고뿐이고, 서류 평가 기준을 밝힌 국내 면접관 글은 못 찾았다.
- [2]의 "WCAG 2.2 AA" 같은 구체 기준은 글쓴이의 예시이므로, 이력서에는 실제로 적용한 버전 · 등급만 쓴다.
