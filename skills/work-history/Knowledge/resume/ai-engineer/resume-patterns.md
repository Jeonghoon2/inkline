# AI 엔지니어 (LLM 애플리케이션 · RAG · 에이전트) — 이력서 패턴 (조사 2026-10-27 · Inkline 이 웹 검색으로 모음)

- 성과는 이 순서로 고릅니다. ① 실서비스에 낸 LLM·RAG·에이전트 기능 ② 평가 체계를 만들어 품질을 수치로 올린 일 ③ 지연·비용을 줄인 일 ④ 장애·품질 저하의 원인을 찾아 고친 일 ⑤ 사내 도구나 PoC. 토이 프로젝트는 맨 뒤에 둡니다.
- 성과 한 줄은 '결과 수치 → 무엇을 → 어떻게' 순서로 씁니다. 예: 'Top-5 검색 Recall ○%→○% / 사내 문서 RAG 검색 / 청킹 단위 변경과 rerank 도입, LLM-as-a-Judge 평가셋 ○건으로 검증'. 수치는 자기 기록에 있는 것만 넣습니다.
- 또 다른 예: 'p95 응답 지연 ○초→○초, 요청당 비용 ○% 절감 / 상담 챗봇 / 모델 라우팅과 캐시, 스트리밍 적용'. 품질·속도·비용 중 무엇을 포기하고 무엇을 얻었는지 한 구절로 덧붙입니다.
- 프로젝트마다 문제(왜) → 내 역할 → 기술 선택 근거 → 성과를 쓰고, 데이터 규모와 트래픽 같은 서비스 환경을 함께 적습니다. 토스 공고의 이력서 안내와 잡플래닛 기사가 모두 이 꼴을 권합니다.
- 평가 방법은 따로 밝혀 둡니다. 평가셋을 어떻게 만들었는지(건수, 출처), 어떤 지표를 썼는지(Recall@K, 정확도, faithfulness 등), 오프라인 결과와 온라인 결과를 씁니다.
- 실패하고 고친 이야기를 한 줄 넣습니다. 예: 할루시네이션이나 검색 누락의 원인을 로그로 찾아낸 뒤 프롬프트나 인덱스를 고친 경험.
- 기술 구역은 LLM·에이전트(API, LangChain/LangGraph, MCP) / 검색·RAG(임베딩, Vector DB, Elasticsearch) / 평가·관측(평가셋, Langfuse, LangSmith 등) / 서빙·인프라(FastAPI, Docker, K8s, vLLM, 클라우드) / 언어 순으로 나눕니다.
- 스택은 넓게 늘어놓지 말고 실제로 깊게 쓴 3~4개 위주로 적습니다. 'ChatGPT 능숙'처럼 도구 이름만 쓰는 것은 정보가 되지 않습니다.
- 백엔드 출신이라면 API 설계, 트래픽, 장애 대응 경력을 LLM 서비스 운영과 이어지게 씁니다. AI 엔지니어 상당수가 LLM 연동을 익힌 일반 소프트웨어 엔지니어라는 관점이 근거입니다(Chip Huyen, Pragmatic Engineer).
