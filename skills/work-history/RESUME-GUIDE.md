# 이력서 작성 가이드

`resume.md` 를 쓰거나 고칠 때 따르는 원칙. 실제 개발자 이력서 가이드·예시에서 공통으로 권하는 것만 모았다 (출처는 맨 아래).

## 구성 (위에서 아래로)
1. **이름 · 한 줄 소개** — 키워드가 든 한 문장. "끊임없이 배우는 개발자" 같은 진부한 말은 쓰지 않는다
2. **연락처 · 링크** — 이메일, GitHub, 포트폴리오/블로그. 사진·주소·생년월일은 넣지 않는다
3. **자기소개** — 2~3줄. 무엇을 잘하는지, 어떻게 일하는지를 이력서 전체를 요약해 쓴다 (마지막에 쓴다)
4. **경력** — 최신순. `회사 · 직책 · 기간`, 그 아래 맡은 프로젝트
5. **프로젝트** — 아래 '프로젝트 쓰는 꼴'(이름 · 소속/기간 · Description · What did I do 3~5개 · Skills)
6. **기술** — 지원 직무와 관련된 것만, 실제 프로젝트에서 쓴 것 위주
7. **교육 · 자격** — 있으면

맨 위 3줄(한 줄 소개 · 자기소개 · 첫 성과)만 읽어도 강점이 보여야 한다. 분량은 1장에 맞추려고 성과를 지우지 않는다 — 2~3쪽까지 허용, 넘으면 줄인다.

## 프로젝트 쓰는 꼴 (사용자가 정한 것, 2026-10-17)
경력 구역에는 `### 회사 · 직책` 과 `기간:`·`역할:` 만 두고, 프로젝트는 그 아래 `## 프로젝트` 구역에 하나씩 이 꼴로 쓴다(기본·직무 이력서 모두).

```markdown
### 프로젝트 이름 (무엇을 만든 시스템인지 알 수 있는 이름)
소속: 예시회사 / 기간: 2026.09 - 현재

**Description**

배경·목적 → 규모·역할·협업 → 핵심 구성 순서로 2~3문장, '~합니다/~하였습니다' 체.

**What did I do**

- **한 일과 결과** — 어떻게 했는지 짧게 (3~5줄)

***Skills***: Python, FastAPI, PostgreSQL
```
- 머리 줄 라벨은 실제 관계대로 — 고객사가 정말 있을 때만 `고객사:`, 아니면 `소속:`(또는 `회사:`). 기간은 `YYYY.MM - YYYY.MM` 또는 `- 현재`
- 이름에는 제품 이름(예: 서비스 공개 이름)을 괄호로 붙이고, Description 첫 문장에서 그 제품이 무엇인지 한 번 풀어 쓴다
- What did I do 는 줄마다 행동 하나 + 결과 하나. 작은 성과 여럿은 의미 있는 줄 하나로 묶는다 — 다 적기보다 읽히는 것이 먼저다. 직무마다 고르는 줄이 다르다
- 숫자는 개발을 모르는 사람에게도 뜻이 있을 때만(예: '보고서 생성 시간 40% 단축', '4.2초 → 0.6초'). 단위·내부 측정값을 늘어놓지 않는다
- 팀 성과와 내 몫을 가른다 — Description 에는 팀 · 규모 · 협업, What did I do 에는 내가 한 일만 쓴다. 팀이 한 일을 내가 한 것처럼 쓰지 않는다
- Skills 는 주력 → 부가 순서. 그 프로젝트에서 핵심으로 쓴 기술이 앞에 온다
- 운영에 나가지 않은 일은 이름 끝에 '(운영 배포 전)'
- 페이지는 이 꼴을 제목 → 회색 머리 줄(소속 │ 기간 (n개월)) → 'Description' 문단 → 'What did I do' 목록 → 'Skills' 칩으로 그린다. 옛 꼴(`#### 프로젝트` + `기간:`·`역할:`·`기술:`)도 그대로 그린다

## 인사 담당자가 읽는 글
이력서는 인사 담당자가 먼저 읽는다. 직접 만든 개발자만 아는 말은 쓰지 않고, 무엇을 했는지 쉬운 말로 바꾼다.

| 쓰지 않는 말 | 예 | 바꿔 쓰기 |
| --- | --- | --- |
| 내부 버전·변경 번호 | V42, v1.4.2, prompt-v3 | 지운다 — 필요하면 '두 차례 운영 배포', 'DB 구조 변경' |
| 주소 경로·API 이름 | (/partner/*), /orders/… | '외부 시스템 연동 API', '신청을 받는 외부용 주소' |
| 파일·함수·클래스·표 이름 | sync.py, buildUrl(), order_reports | 하는 일로: '보관 작업', '리포트 표' |
| 커밋·MR 번호, 브랜치 | 9f3c1e7, !52, dev/1.4.0 | 지운다 |
| 환경 변수·명령 옵션 | API_BASE_URL, --dry-run | '연동 주소 설정', '미리 보기 실행' |
| 내부 코드명 | svc-be, 규칙 v3 | '주문 서버', '결제 중복 막기 규칙' |
- 제품의 공개 이름(예: 서비스 공개 이름)과 누구나 아는 기술 이름(React · AWS · PostgreSQL)은 쓴다. 기술 이름은 Skills 줄에 모은다
- 처음 보는 사람에게 낯선 말은 괄호로 한 번 풀이한다(예: '날짜별 압축 파일(Parquet)', '국제 보안 기준(OWASP Top 10)')
- **검사:** `node ~/My-History/build.mjs` 가 이력서 파일(보완할 경험 포함)에서 위 말을 정규식으로 찾아 '이력서 개발자 용어 N곳'과 파일:줄을 경고한다(규칙은 `site/build.mjs` 의 `JARGON`). 0곳이 될 때까지 고친다. 정규식이 못 잡는 말(로컬, 멱등, 오탐 같은 업계 용어)은 마지막에 한 번 인사 담당자처럼 읽어서 고친다

## 성과 한 줄 쓰는 법
- **결과(수치) → 무엇을 → 어떻게** 순서. 구글 XYZ 공식("Y로 측정된 X를 Z를 해서 이뤘다")을 한국어 어순에 맞춘 것
  - 좋음: `목록 API 응답 70% 단축 (2.0 → 0.6초) — 필요한 열만 읽도록 변경`
  - 나쁨: `확장 프로세스 구조를 개선했습니다`
- 수치는 **전 → 후**와 **비율**을 함께. 측정 조건(횟수·환경)이 있으면 짧게
- 기술 이름보다 **가치(사용자·운영·비용에 준 영향)**를 먼저
- 한 줄에 하나. 줄글·긴 문장 금지, 동사로 끝나는 명사형(…단축, …제거, …설계)
- 성능 수치는 기준(전)과 측정 조건을 함께 쓴다. 여러 변경을 묶어 한 변경의 효과처럼 쓰지 않는다(인과 과장 — 예: 프레임워크 교체와 인덱스 최적화를 묶어 '전환해서 60% 감소')
- 흔한 경험의 나열보다 **나만 한 문제 해결**(원인을 찾은 과정, 판단의 근거)을 고른다
- 기능 작업은 큰 제목으로 묶어 한 줄씩, 성과가 수치로 남은 일을 위로

## 하지 않는 것
- 확인되지 않은 수치·표현 (예: 재지 않은 '무중단', 쓰지 않은 도구 이름)
- 지어낸 개인정보 — 모르는 칸은 `[대괄호]`로 남긴다
- 모든 일을 다 적기 — 프로젝트마다 핵심 3~5개
- 면접에서 1분 안에 설명하지 못할 줄·수치 — 줄마다 '왜 그 수치가 나왔나'에 답할 수 있어야 한다
- 용어 부풀리기 — 큐에 쌓는 것을 'backpressure', 브로커 도입을 'SPOF 제거', 'exactly-once' 를 근거 없이 쓰지 않는다
- 잰 근거 없는 정밀 수치 — '생산성 3배', '논의 80% 감소'. 잰 방법을 말할 수 없으면 뺀다

## 직무별 이력서 (백엔드 · 프론트엔드 · 데이터 엔지니어 · AI 엔지니어)
근거 자료는 `Knowledge/resume/INDEX.md`(공고 표본·채용 가이드 요약·점검표). 쓰기 전에 그 직무 폴더의 `resume-patterns.md` 와 `checklist.md` 를 읽는다.
- **기본(`resume.md`)은 그대로 두고** 직무마다 `~/My-History/resume/<직무>.md` 를 따로 쓴다. 같은 사실을 **고르고 · 순서를 바꾸고 · 말을 바꾸는 것**이지 사실을 더하지 않는다(원티드도 직무별 2~3 버전을 권한다)
- 사실의 근거는 기록(`~/My-History/*/YYYY-MM.md`)·resume.md·저장소 git 이력(읽기만)뿐. 회사·기간·숫자·기술 이름을 지어내지 않고, 모르는 칸은 `[대괄호]`
- 운영에 나간 일과 개발 환경·설계에서 멈춘 일을 가른다 — 배포 전이면 프로젝트 제목이나 줄 끝에 '(운영 배포 전)'

| | 백엔드 | 프론트엔드 | 데이터 엔지니어 | AI 엔지니어 |
| --- | --- | --- | --- | --- |
| 맨 위에 둘 성과 | 운영 장애·성능 해결(원인 → 근거 → 수치) | 성능 숫자(번들·렌더링·CLS), 재현해 없앤 결함 | 끝에서 끝까지 파이프라인(규모·주기·정합성) | 운영 LLM 기능 + 품질을 잰 방법 |
| 그다음 | DB 깊이(잠금·인덱스·거래·마이그레이션), 보안, 테스트·배포 | 구조(계약 검사·오류 경계·공용 부품), 품질 체계, 화면 개편은 한 줄로 | 대용량 처리, 품질·이상 데이터, 읽기 경로, 거버넌스 | 생성-평가 고리, 주입·개인정보 방어, 비용·지연 |
| 숫자 | 응답 시간(초·p95), 메모리, 장애 시간, 실패 0, 테스트 수 | MB·KB, px, 건수, 화면 상태 점검 수 | 행·파일 수, 메모리 피크, 건수 일치, 조회 시간 | 차단·오류 수 전 → 후, 통과율, 토큰·$, 초 |
| 기술 구역 | 언어·프레임워크 / DB / 클라우드(서비스 이름) / 테스트·CI / 보안 | 6~10개로 짧게, 데스크톱은 분류를 따로 | 언어·SQL / 저장·형식 / 처리·스케줄 / 품질 / 클라우드·IaC | 모델·API / 기법 / 평가 / 비용·운영 / 백엔드 |
| 간단 소개(2~4줄) | 운영 데이터로 원인을 찾는 사람 + 대표 수치 + 두 스택 | 숫자로 재고 고치는 사람 + 웹·데스크톱 + 대표 수치 | 잃지 않고 옮기고 검증하는 사람 + 규모 수치 | 검사·평가로 믿게 만드는 사람 + 품질 수치 + 운영 여부 |
- 다른 직무에 강한 성과는 빼지 말고 **아래로 내리거나 한 줄로 묶는다**(예: 백엔드 이력서의 프론트엔드 프로젝트는 성능 두 줄만)
- 간단 소개의 세 줄 꼴: 직무 + 잘하는 것 → 대표 성과 1~2개(숫자) → 일하는 방식
- 직무 공고가 쓰는 단어(`job-posting-patterns.md`)를 실제로 한 일의 줄 안에 쓴다. 안 써 본 도구는 기술 구역에 넣지 않고 '보완할 경험'으로 보낸다

## 보완할 경험 (오른쪽 아래 말풍선)
직무 파일 끝의 `## 보완할 경험` 구역. 화면·인쇄 이력서에는 나오지 않고 말풍선에만 보인다.
1. 그 직무의 `Knowledge/resume/<직무>/checklist.md` 항목마다 **증거 키워드**를 기록에서 찾는다
2. 판정: 운영 수치까지 있으면 '있음', 구현·로컬·설계만이면 '약함', 없으면 '없음'
3. `### 부족한 경험` — '없음'·'약함' 중 공고 빈도가 높은 것 4~5개. 한 줄에 '무엇이 없는지 — 왜 중요한지(공고 근거)'
4. `### 해보면 좋은 것` — 이미 있는 프로젝트(저장소·환경 이름까지)에서 하루~이틀이면 되는 작은 다음 걸음 4~5개. 해 보면 이력서 숫자가 생기는 일로
5. 기록에 새 증거가 생기면 그 항목을 지우고, 점검표의 다음 항목을 올린다

## AI·ATS 스크리닝 대비 (2026-10-17 점검에서 정한 것)
- **PDF 글자로 확인한다** — 'PDF로 저장'(또는 머리 없는 Chrome `#cv=<직무>`)으로 뽑은 PDF 를 `pdftotext` 와 pypdf 로 풀어 읽는다. 한글 사이가 벌어지거나(조각 웹 글꼴), 기술 칩 사이에 다른 구역이 끼거나, 연락처 이름이 아이콘에만 있으면 렌더러 문제다(site/DESIGN.md 인쇄). 보완할 경험 글자가 PDF 에 없어야 한다
- **구역 제목은 표준 이름** — 자기소개 · 경력 · 프로젝트 · 기술 · 교육 · 자격. 기간은 모두 `YYYY.MM - YYYY.MM|현재`
- **공고 단어를 알아보는 꼴로** — 'Spring Boot', 'CI/CD', '테스트'(소프트웨어 시험은 '시험' 대신 '테스트'), '트랜잭션', '마이그레이션', '코드 분할·지연 로딩', '프롬프트 엔지니어링', 'ETL·백필'처럼 공고가 쓰는 말을, 기록에 그 일이 있을 때만 쉬운 설명과 함께 쓴다. 기록에 없는 공고 단어는 보완할 경험으로
- **숫자끼리 서로 깎아 먹지 않게** — 같은 이력서 안에서 한 숫자가 다른 숫자의 뜻을 바꾸면 하나를 뺀다(예: '가입자 10만 명 달성'과 '휴면 계정 9만 개 정리'를 같이 쓰면 가입자 대부분이 휴면이었다는 뜻이 된다 → 가입자는 '월 활성 1만 명'으로). 다시 만든 범위는 기록 그대로(전부가 아니면 '3월분 300건')
- **학생 톤 금지** — '~하고 싶습니다', '~하겠습니다', '흥미를 느꼈습니다', '배우고 싶다'. '해결해 왔습니다', '기여할 수 있습니다'처럼 한 일과 할 수 있는 일로 쓴다
- **AI 가 쓴 것 같은 말 금지 목록** — '혁신적인', '다양한', '다각적', '포괄적', '심층적', '체계적', '뛰어난', '효율적으로'(결과 없이), '~을 통해 ~을 달성', '시너지', '극대화', '숫자로 증명합니다'(모든 소개에 되풀이), 번역투('끝에서 끝까지' → 'E2E(전 구간)', '평가 고리' → '평가 루프'), 한 문장에 같은 낱말 두 번('검증 … 검증'). 동음이의로 잘못 읽히는 말도 피한다('재고 고치는' → 재고(在庫)로 읽힌다)
- **띄어쓰기** — 영문·숫자 뒤 조사는 붙인다('AWS에서', 'React로', 'Parquet에')
- **성과 줄에 줄표(—)를 쓰지 않는다** — 굵은 결과 뒤는 콜론(`**조회 4.2초 → 0.6초**: 보관 파일에서 읽도록 변경`). 줄표는 AI 가 쓴 글의 표지이고, 결과 · 방법 · 검증을 한 줄에 줄표로 잇는 것이 길어 보이는 원인이다. 검증 근거가 길면 괄호로 짧게 붙이거나 줄을 줄인다
- **성과 줄 끝은 명사형 하나로** — '…통합', '…변경', '…차단'. '합침·보여 줌·막음' 같은 '-ㅁ' 끝과 섞지 않는다. Description 은 '~했습니다'로 맞춘다('하였습니다'와 섞지 않는다)
