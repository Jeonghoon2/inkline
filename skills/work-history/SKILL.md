# 작업 기록 (~/My-History)

**나눠 두기:** `~/My-History` 에는 데이터(기록·사전·보고·이력서·쇼츠 결과)만 둔다. 페이지를 만드는 코드(`site/build.mjs`·`template.html`·`src/`), 서버(`site/serve.mjs`), 디자인 규칙(`site/DESIGN.md`), 이력서 원칙(`RESUME-GUIDE.md`)은 이 스킬 폴더에 있다. My-History 의 `build.mjs`·`serve.mjs` 는 스킬을 부르는 진입 파일이다

## 처음 한 번 / 다른 컴퓨터에서
- **다른 컴퓨터로 옮길 때:** 이 스킬과 concept-shorts 를 `~/.claude/skills/` 에 두고, 예전 기록 폴더에서 **데이터만**(`<카테고리>/<YYYY-MM>.md` · `concepts.md` · `reports/` · `resume.md` · `resume/` · `README.md` · `shorts/*.mp4·*.json`) `~/My-History` 로 복사한 다음 아래 init 을 돌린다. 처음이면 빈 채로 init 만
- `node ~/.claude/skills/work-history/site/init.mjs [기록 폴더]` (기본 `~/My-History`) — 폴더 뼈대(README 카테고리 표·concepts.md·reports/)와 진입 파일을 만들고 페이지를 만든다. 이미 있으면 진입 파일만 다시 쓰고 데이터는 건드리지 않는다. 스킬 폴더를 옮겼으면 다시 돌린다
- 서버: `node ~/My-History/serve.mjs` → `http://localhost:4173` (다른 포트는 `PORT=4180 node …`, 끄기는 Ctrl+C). 주소: `/` 페이지 · `GET /api/shorts` 만든 쇼츠와 진행 중인 작업 · `POST /api/shorts?name=<개념>` 쇼츠 만들기(같은 페이지에서만) · `/shorts/<파일>.mp4·.json`. 기록 폴더를 바꾸려면 `--root <폴더>` 또는 `MH_ROOT`
- 필요한 것: Node 18+ 하나(외부 패키지 없음). 쇼츠까지 쓰려면 concept-shorts 스킬을 같은 skills 폴더에 두고 그 `engine/setup.sh`(Windows 는 `node …/engine/setup.mjs`)
- **검증:** `node ~/.claude/skills/work-history/site/verify.mjs [기록 폴더] [--full]` — 빈 임시 HOME 에 스킬 두 개와 데이터만 옮겨 다시 만들고, 페이지(index.html, 만든 시각 빼고 한 글자까지)·서버(페이지·쇼츠 목록·영상 넘겨 보기·다른 사이트 요청 막기)·스킬 문서의 옛 경로를 원본과 비교한다. `--full` 은 쇼츠 엔진 설치와 쇼츠 한 편 다시 녹화(프레임 비교)까지. 코드·디자인을 고친 뒤 돌린다

## 언제
- **자동:** 이 스킬 폴더의 `rules.json` 의 `auto` 값을 따른다(Inkline 앱 환경설정 '작업 기록을 남기는 때'에서 고친다). 파일이 없거나 깨졌으면 기본값 — `mergeMain`·`mergeIntegration`·`release`·`troubleshooting` 켬, `taskDone` 끔
  - `mergeMain`: main(기본 브랜치)에 머지한 직후 · `mergeIntegration`: 통합 브랜치(develop 등)에 머지한 직후 · `release`: 배포(릴리스·태그)를 마친 직후
  - `troubleshooting`: 아래 '트러블슈팅' 건 · `taskDone`: 머지·배포가 없어도 코드 작업 하나를 마쳤을 때(질문·조사·설명은 빼고)
  - 꺼진 항목은 자동으로 남기지 않는다(사용자가 요청하면 남긴다). 그 밖의 작업(질문·조사·작은 수정)도 자동으로 남기지 않는다
- **트러블슈팅**(`troubleshooting` 이 켜져 있을 때)**:** 운영 장애나 예상 못 한 실패(작업이 죽음, 배포 실패, 데이터 문제 등)의 원인을 찾아 해결해 배포까지 마치면, 머지·배포 기록과 **별도로** 트러블슈팅 한 건을 남긴다(아래 '트러블슈팅 형식')
- **요청:** "기록해 줘", "주간 보고", "이번 주/지난주 작업 정리"

## 기록 남기기
1. 카테고리를 정한다 — 작업한 git 저장소(또는 폴더) 이름 기준. `~/My-History/README.md`의 카테고리 표를 먼저 보고, 이미 있는 이름을 쓴다. 없으면 새 폴더를 만들고 표에 한 줄 추가(`| 카테고리 | 대상 |` — 대상은 무엇을 하는 곳인지 한 줄, 저장소가 있으면 괄호에 경로, 예: `| ShopAPI | 쇼핑몰 주문 API 서버 (org/shop-api) |`). 표는 사람이 보는 목록이고 페이지는 폴더 이름으로 카테고리를 만든다 — 그래도 같은 이름을 다시 쓰게 표를 먼저 본다)
2. `~/My-History/<카테고리>/<YYYY-MM>.md`에 추가한다 (없으면 `# <카테고리> — YYYY년 M월` 제목으로 만든다)
   - 오늘 날짜 `## YYYY-MM-DD`가 없으면 파일 끝에 만들고, 있으면 그 아래 끝에 붙인다
   - 한 건 형식 (카드에는 종류·내용만, 카드를 누른 상세 창에는 아래 전부가 나온다):
     ```markdown
     ### <종류> — <짧은 제목>
     - 종류: 기능 | 수정 | 성능 | 배포 | 문서 | 조사 | 트러블슈팅
     - 분류: <대분류> - <소분류>, <대분류> - <소분류>
     - 내용: 무엇을 했고 결과가 어땠는지 한두 줄 (수치·버전이 있으면 그대로)

     #### 수행 일지
     - 한 일을 순서대로 (없으면 상세 창에 '내용' 줄을 대신 보여 준다)

     #### 고민한 흔적
     - 막힌 점, 원인을 찾은 과정, 고른 방법과 그 근거

     #### 성능 비교/평가/측정
     - 지표: 전 → 후 (비율), 측정 조건
     ```
   - 분류는 기존 기록에서 쓰던 이름을 먼저 고른다 (대분류: 프론트엔드·백엔드·데스크톱 앱·성능·배포·문서·AI·보안, 소분류: 기술·도구 이름). 상세 창에서 누르면 그 분류로 거른다
   - 세 섹션은 해당 내용이 있을 때만 쓴다(빈 섹션은 창에서 숨는다). 특히 고민·수치는 커밋·문서·측정으로 확인한 것만 — 지어내지 않는다
   - **근거를 참고한 작업**(논문 · 연구 · 지침 · 조사 · 비교 자료를 보고 바꾼 것)은 수행 일지에 채택한 것마다 한 줄로 `<무엇을 채택> — 근거: '<제목>'(<저자> <연도>) <쪽 · 절 · 장이나 표 번호>` 를 적는다. 쪽을 확인하지 못했으면 '쪽 미확인'이라고 적는다(지어내지 않는다). 주간 보고가 이 줄로 '채택 · 근거'를 만든다. 그 근거가 지식사전(`knowledge` 스킬, ~/My-History/knowledge)에 있으면 줄 끝에 `(지식사전: <분류>/<slug>)` 를 붙이고, 없으면 지식사전에 먼저 저장한다
   - **모든 종류를 누구나 이해할 수 있게, 상세하게 쓴다** (개발을 모르는 사람이 읽어도 왜·무엇을·결과를 알 수 있게):
     - 평서체('~했다'), 짧은 문장. 한 줄은 명사 나열이 아니라 완결된 문장 한두 개
     - 내용: 2~3문장(왜 필요했나 → 무엇을 했나 → 결과 수치), 반드시 한 줄
     - 수행 일지: '무엇을 바꿨고 그래서 사용자에게 무엇이 달라졌는지', 고민한 흔적: '문제 → 원인 → 고른 방법과 이유'
     - 성능: `지표: 전 → 후 (비율) — 무슨 뜻인지 한 마디`
     - 기술 용어·약어·파일 이름은 빼거나 처음 나올 때 괄호로 풀이(예: 'IPC' → '앱 안 프로세스끼리 주고받는 메시지(IPC)', '목' → '실제 서버 대신 쓰는 가짜 응답'). 수치·버전·MR 번호는 그대로
     - 렌더러는 `- ` 평평한 목록과 `**굵게**`, 형광펜 `==…==`만 그린다 — 들여쓴 하위 목록·표·`#####` 금지
   - **형광펜 개념:** 원리를 알아야 이해되는 대목이나 면접에서 물어볼 만한 대목(예: 종료 코드 137, 나눠 읽기, 멱등성)은 `==보이는 글자|개념 이름==`으로 칠한다(이름을 빼면 글자가 곧 이름). 마우스를 올리면 원리가 뜨고, 상세 창 맨 아래에 '면접 꼬리 질문'이 모인다
     - 개념은 `~/My-History/concepts.md` 한 곳에 둔다. 이미 있는 이름이면 다시 쓰지 않고, 없으면 `## 개념 이름` + 원리 문단(쉬운 말 3~4문장) + `- Q:`/`  A:` 꼬리 질문 3~4개(앞 질문의 답을 파고드는 순서)를 보탠다
     - 우리 코드에 대한 답은 코드로 확인한 것만 쓴다. 일반 원리는 정확한 것만 쓴다. build.mjs 가 사전에 없는 이름을 경고한다
   - 같은 날 같은 기능의 연속 머지(예: 고친 뒤 다시 머지)는 새 건을 만들지 말고 기존 건의 내용을 보탠다
   - 비밀번호·API 키·토큰 값, 고객 개인정보는 적지 않는다
   - **트러블슈팅 형식** — 섹션이 다르다. 상세 창도 상황 → 문제 → 해결 과정 → 고민한 흔적 순으로 보인다:
     ```markdown
     ### 트러블슈팅 — <무슨 문제를 해결했는지 쉬운 말로>
     - 종류: 트러블슈팅
     - 분류: <대분류> - <소분류>, ...
     - 내용: 무슨 일이 있었고 어떻게 고쳤는지, 결과 수치 한두 줄

     #### 상황
     - 무엇을 하던 중이었는지(작업·환경·규모)

     #### 문제
     - 무슨 일이 일어났는지(증상, 오류 번호와 그 뜻), 어디까지 진행됐었는지

     #### 해결 과정
     1. **원인 찾기** — 어떻게 원인을 좁혔는지
     2. **피해 확인** — 데이터·서비스에 영향이 있었는지
     3. **해결 방법 고르기** — 다른 방법과 비교해 왜 이 방법인지
     4. **수정** — 무엇을 어떻게 바꿨는지
     5. **효과 측정** — 전 → 후 수치(측정 조건)
     6. **배포** — 테스트·버전

     #### 고민한 흔적
     - 추정에 그친 것은 '(추정)'으로 표시, 남은 확인할 일
     ```
     - 쉬운 말 규칙은 위와 같다(예: 'yield_per' → '5천 줄씩 나눠 읽기', '137/SIGKILL' → '메모리를 다 써서 시스템이 강제로 끈 경우의 번호')
     - 해결 과정 단계는 실제로 한 것만 쓰고, 해당 없는 단계는 뺀다. 같은 문제의 후속 확인은 새 건을 만들지 말고 이 건에 보탠다
     - 예시: concept-shorts 스킬의 `examples/ShopAPI/2026-10.md`(야간 정산 작업이 메모리 부족으로 멈춘 문제 해결)
3. `node ~/My-History/build.mjs`로 타임라인 페이지(index.html)를 다시 만든다
4. 사용자에게는 한 줄로만 알린다 (예: "작업 기록에 남겼습니다: ShopAPI · 결제 중복 방지")

## 주간 보고 만들기
`~/My-History/*/<해당 월>.md`에서 기간 안의 기록을 모아 `~/My-History/reports/<YYYY>-W<주>.md`(비개발자용은 `<YYYY>-W<주>-비개발자.md`)로 쓰고 build.mjs를 다시 돌린다. Inkline 앱의 주간 보고 탭 [주간 보고 만들기]도 같은 형식으로 만든다. 형식(사용자가 정한 것):

```markdown
# 주간 보고 — <YYYY>-W<주> (<첫 기록 M.D> ~ <끝 기록 M.D>)

**○ <카테고리> (<시작 M.D> ~ <끝 M.D>)**

- <주제>: <그 주제에서 한 일 한 문장>
- <주제>: <그 주제에서 한 일 한 문장>
```
- 프로젝트(카테고리)마다 큰 제목 하나, 그 안에 비슷한 기록을 묶은 주제(배포, 기능 영역, 성능, 문서 …) 2~6줄
- 개선 · 수정 · 성능처럼 무언가를 바꾼 주제는 `- <주제>: <기존 방식 · 문제> → <바꾼 방식>` 으로 쓰고, 근거(조사 · 연구 · 비교 · 의견)를 보고 바꿨으면 두 칸 들여쓴 하위 줄로 `  - 참고: …` · `  - 채택: <무엇을>` · `  - 이유: <왜>` · `  - 이점: <무엇이 좋아졌나, 수치>` 를 붙인다(기록에 있는 것만, 없는 줄은 뺀다). 새 기능은 한 줄 요약. 주간 보고의 하위 줄은 페이지가 들여 그린다(기록 본문은 여전히 평평한 목록만)
- 대상을 묻거나 사용자가 정한다 — **개발자용**: 기술 이름 · 버전 · 수치 그대로(파일 · 함수 · 내부 코드명은 빼고). **비개발자용**: 전문 용어를 쉬운 말로(머지 → 반영, 배포 → 새 버전 공개, CI → 자동 검사), 결과 중심, 수치는 뜻을 덧붙여. 제목 줄에 ` · 비개발자용`
- 사용자가 "간략하게"라고 하면 주제마다 한 줄을 더 짧게, 수치는 % 등으로
- 보고 본문은 채팅에도 그대로 보여 준다 (붙여 넣어 쓰도록)

## 이력서
- `~/My-History/resume.md` 하나가 페이지의 '이력서' 탭이 된다 (탭: 타임라인 · 주간 보고 · 이력서)
- 형식: `# 이름`, `> 한 줄 소개`, 그 아래 `- 항목: 값` 연락처, `## 구역`(자기소개·경력·프로젝트·기술·교육 · 자격). 경력은 `### 회사 · 직책` + `기간:`·`역할:`. **프로젝트는 `## 프로젝트` 아래 `### 이름` → `소속: 회사 / 기간: YYYY.MM - 현재`(고객사가 정말 있을 때만 `고객사:`) → `**Description**` 2~3문장(합니다체) → `**What did I do**` 3~5줄 → `***Skills***: a, b`** (자세히는 RESUME-GUIDE '프로젝트 쓰는 꼴'). 옛 꼴(`#### 프로젝트` + `기간:`·`역할:`·`기술:`)도 그려진다. `[대괄호]`는 아직 안 채운 칸으로 노랗게 보인다. 이름에 '기술'·'스킬'이 든 구역의 `- 분류: a, b, c` 줄은 칩으로 보인다(괄호 안 쉼표는 나누지 않는다). `기간:` 이 `YYYY.MM - YYYY.MM|현재` 꼴이면(`~` 도 읽는다. 경력·프로젝트·교육 모두 ` - ` 하나로 맞춘다) 경력 회사 옆과 경력 제목 옆에 기간(n년 m개월)을 붙인다
- **인사 담당자가 읽는 글:** 내부 버전(V42 · v1.4.2), 주소 경로(/partner/*), 파일·함수·표 이름, 커밋·MR 번호, 환경 변수·명령 옵션, 내부 코드명을 쓰지 않고 하는 일로 바꾼다('외부 시스템 연동 API', '결제 중복 막기 규칙'). build.mjs 가 이런 말을 '이력서 개발자 용어 N곳'으로 경고한다 — 0곳으로 만든다(RESUME-GUIDE '인사 담당자가 읽는 글')
- **쓰기 전에 이 스킬의 `RESUME-GUIDE.md` 를 따른다** — 성과는 '결과 수치 → 무엇을 → 어떻게' 한 줄, 기능은 큰 제목으로 묶고 수치 있는 성능 작업을 위로, 확인 안 된 수치·표현과 지어낸 개인정보 금지
- 기록에서 큰 작업·수치 있는 성과만 골라 올리고, '어떻게'는 저장소 커밋·문서로 확인한 사실만 쓴다
- 사용자가 "이력서 갱신해 줘"라고 할 때 고친다 (자동으로 고치지 않는다). 고친 뒤 build.mjs 를 다시 돌린다
- **직무별 이력서:** `~/My-History/resume/<직무>.md`(`backend` · `frontend` · `data-engineer` · `ai-engineer`, 다른 이름도 되고(영문 소문자·숫자·`-`) 그때는 칩에 파일 이름이 보인다). 형식은 resume.md 와 같고 두 가지만 다르다
  - `# 이름`·연락처(`- 항목: 값`)를 빼면 resume.md 의 것을 쓴다 — 연락처는 resume.md 한 곳에서만 고친다. `> 한 줄 소개`는 직무마다 쓴다
  - 끝의 `## 보완할 경험` 구역(`### 부족한 경험` · `### 해보면 좋은 것` 아래 `- **제목** — 설명`)은 이력서에 그리지 않고 오른쪽 아래 '보완할 경험 N' 말풍선에만 보인다(N = 부족한 경험 수)
  - 쓰는 법·고르는 순서·보완할 경험 판정은 `RESUME-GUIDE.md` 의 '직무별 이력서'·'보완할 경험', 근거 자료는 `Knowledge/resume/INDEX.md`(직무별 공고 패턴·점검표)
- 이력서 탭 위 칩(기본 · 백엔드 · 프론트엔드 · 데이터 엔지니어 · AI 엔지니어)으로 바꿔 보고, 고른 직무는 브라우저에 기억한다(`mh-cv-role`). 주소 끝 `#cv=backend` 로 바로 열 수 있다 — 머리 없는 Chrome 으로 직무 PDF 를 뽑을 때 쓴다(`chrome --headless=new --no-pdf-header-footer --print-to-pdf=cv.pdf 'http://localhost:4173/#cv=backend'`). 'PDF로 저장'은 고른 직무 이력서만 찍는다

## 타임라인 페이지
- `~/My-History/index.html`을 브라우저로 열면 된다 (`open ~/My-History/index.html`, Windows 의 Git Bash 는 `explorer.exe "$(cygpath -w ~/My-History/index.html)"`). 쇼츠를 만들려면 `node ~/My-History/serve.mjs` 뒤 `http://localhost:4173` (concept-shorts 스킬)
- 화면 짜임 (Ink & Highlighter):
  - 머리: 갱신 시각 · '작업 기록' · 탭(타임라인 · 주간 보고 · 이력서)
  - 타임라인: 개요(이번 주 요약 · 최근 8주 활동 지도 · 숫자 4칸) → 거르기(종류 탭과 건수 · 프로젝트 · 검색 · 카드/압축) → 날짜 칸 목록
  - 상세 창: 기사형 본문(라벨 · 제목 · 요약 · 쇼츠 띠 · 섹션 · 면접 꼬리 질문) + 오른쪽 칸(날짜 · 프로젝트 · 이 기록의 개념 · 같은 날 기록)
  - 이력서: 위에 직무 칩, 원티드 이력서 같은 1단 문서(이름 · 연락처 · 소개 → 구역 차례로), 직무 이력서면 오른쪽 아래 '보완할 경험' 단추와 말풍선. 경력의 `###` 회사는 아이콘 칸 + '기간 (n년 m개월) │ 역할', 프로젝트는 제목 · 회색 머리 줄(소속 │ 기간) · 'Description' · 'What did I do' · 'Skills' 칩(옛 꼴 `####` 은 들여 쓰고 `기술:` 은 끝줄 '사용 기술'), 기술 구역의 `- 분류: a, b` 는 칩. 'PDF로 저장'은 A4 — 직무 이력서는 2쪽을 넘기지 않게 쓴다
- **모양을 바꿀 때는 이 스킬의 `site/DESIGN.md` 를 먼저 읽는다** — 어느 색 토큰을 언제 쓰는지, 한글 라벨에 고정폭 글꼴 금지, 그림자 금지, 글자가 흐르는 칸에 flex 금지, 하지 않기로 한 것. 고친 뒤 DESIGN.md 도 같이 고친다.
- 코드(이 스킬의 `site/`): `src/styles/*.css`(`base` 토큰·공통 · `timeline` · `reports` · `resume` · `shorts`)·`src/scripts/*.js`(뼈대는 `template.html`)를 고치고 `node ~/My-History/build.mjs` 를 다시 돌린다 (index.html은 매번 새로 만들어진다). 새 조각 파일은 `site/build.mjs`의 `STYLES`·`SCRIPTS` 목록에 순서대로 추가. 고친 뒤 `site/verify.mjs` 로 확인
- 고친 뒤 브라우저로 밝은·어두운 테마와 휴대폰 너비(390px)를 열어 본다 — 가로 넘침, 겹친 글자, 콘솔 오류
